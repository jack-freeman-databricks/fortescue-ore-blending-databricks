# Fortescue ore blending: train load-out grade compliance on Databricks

> **All data is synthetic** and generated by `data_gen/generate.py` (seed 42). Product names (Fortescue Blend,
> Kings Fines) and hub names are Fortescue's public names. Specs, penalty schedule, tonnages and every number
> in this repo are **illustrative**. No Fortescue data or customer content is used. Not an official Fortescue artefact.

## The problem

Fortescue sells iron ore to specification. Ore from four Pilbara mine hubs (Cloudbreak, Christmas Creek,
Solomon, Eliwana) goes to ROM stockpiles, and load-out controllers build each ~34.5 kt train by choosing
which stockpiles to reclaim. Trains rail to Herb Elliott Port and are blended into vessel cargoes.

Controllers decide with the signals they have at the time, and both are biased:

* **Block model** stockpile grade. At Solomon it over-states Fe by **~0.45%**.
* **Cross-belt analyser**, which drifts between calibrations.

The **lab assay**, the grade that counts, arrives **24-48 h after the train leaves**, when the ore is already at port.
The result is that **80% of Solomon Fortescue Blend trains and 72% of Kings Fines trains land below typical Fe**,
vessels miss spec, and iron is given away at the hubs that over-deliver.

## The solution: one integrated data journey

```
 FMS hauls ─┐                                                     ┌─► Genie Agent (NL questions, governed)
 Rail       │  Lakeflow SDP   ┌──────── Unity Catalog ────────┐   │
 Analyser ──┼─► bronze ─► silver (expectations) ─► gold ─► metric views ─┤
 LIMS lab   │   Auto Loader   │ row filter by hub, column mask │   │
 Port       ┘                 │ on penalty $, tags, lineage    │   └─► ML: train_grade_predictor@champion (MLflow/UC)
                              └────────────────────────────────┘         + LP blend optimiser + ai_query rationale
                                         │ synced tables (Delta → Postgres)          │
                                         ▼                                           ▼
                               Lakebase (operational serving) ◄──── recommendations, predictions
                                 ops.blend_decisions / ops.stockpile_availability (app writes)
                                         │                         ▲
                                         ▼                         │ decisions → Delta (audit, retraining)
                               Databricks App "Blend Control Room" ┘
```

## Reproduce

```bash
python data_gen/generate.py --out data/landing                      # synthetic raw data
databricks fs cp -r data/landing dbfs:/Volumes/jack_freeman_catalog/fmg_ore_blending/landing/
python scripts/run_sql.py sql/01_governance_setup.sql               # entitlements, row filter, mask
databricks bundle deploy && databricks bundle run ore_blending_pipeline
python scripts/run_sql.py sql/03_semantic_layer.sql                 # metric views + tags
jupyter nbconvert --execute notebooks/01_train_grade_model.ipynb    # train + register @champion
jupyter nbconvert --execute notebooks/02_score_and_recommend.ipynb  # predictions, blends, ai_query, backtest
bash scripts/setup_lakebase.sh                                       # project, synced tables, grants
python scripts/create_genie.py                                       # Genie Agent
databricks bundle deploy && databricks apps deploy <app> --source-code-path <bundle>/files/app
```

Workspace: FEVM `fevm-serverless-stable-1s8h43` (AWS us-east-1, serverless). Catalog `jack_freeman_catalog`,
schema `fmg_ore_blending`. The app is deployed into the existing app slot `fortescue-maintenance-runner`
because the FEVM account is at its service-principal cap. That slot sits in a shared Apps space that allows no
app resources, so access is granted explicitly (`sql/04_app_grants.sql`, `scripts/setup_lakebase.sh`), and Genie runs
on behalf of the signed-in user so UC row filters and masks apply per person.
